先判斷問題，再選技能

你的第一個教學目標：聽到團隊的工程情境後，能說出「眼前最需要解決的問題」與「下一個適合的技能」。

Matt Pocock 在官方 README用四種常見失敗描述這套技能為何存在：需求沒對齊、代理人說得太囉嗦、程式跑不起來，以及架構逐漸失控。把它們當成診斷問題的入口，比背技能名稱容易。

你看到的徵兆先想到的能力官方例子
大家對功能的意思各說各話釐清意圖與專案語言grill-with-docs、domain-modeling
已有明確需求，但缺少可執行計畫把共識轉成規格與小任務to-spec、to-tickets
功能或修正的正確性沒有回饋建立可觀察的測試迴圈tdd；難解 bug 用 diagnosing-bugs
每次修改都牽動很多模組找清楚模組邊界codebase-design、improve-codebase-architecture

技能可以串接，但順序由問題決定

例如團隊要加「取消訂閱」功能，產品經理、客服與工程師對「取消」是否立即生效意見不同。先用 grill-with-docs釐清詞義與決策；有共識後用 to-spec記錄規格，再用 to-tickets拆小工作。開始實作時，implement會在約定的接縫使用 tdd，最後用 code-review檢查規格與程式標準。這條組合取自官方 README 技能索引中的職責說明。

釐清語意→寫成規格→拆成任務→實作與測試→審查
今天先記住：技能是可組合的工作方法。選擇依據是目前的瓶頸；同一個專案在不同階段可能需要不同技能。完整清單請看技能速查表。

實戰題：請先自己作答

團隊收到一張 ticket：「會員可以暫停方案」。有人認為暫停後立刻停止扣款；有人認為本期結束才停；工程師已準備新增資料庫欄位。你會先選哪個技能？接著可能接哪兩個技能？請用 2–4 句說明你判斷的瓶頸與順序。

請把答案回覆給我。我會根據理由給回饋，再決定第二課從哪個技能切入。也可以直接問我任何看不懂的地方。
