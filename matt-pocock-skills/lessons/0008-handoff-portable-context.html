handoff：讓工作能移交

一段對話累積了很多決策，但接下來要由另一個 agent、另一個環境或同事接手。handoff把目前工作整理成一份可以帶走的 Markdown 文件。

先判斷：工作會不會移動？

Matt 的 AI Hero 說明列出幾個適用情境：換 agent 工具、換資料夾或 repository、交給同事、把目前發現的支線任務交給第二個 agent。若仍在同一工作脈絡中繼續，該文章建議使用環境自己的壓縮機制，而不是為了「摘要」就建立交接檔。

情境選擇原因
在同一個 agent 與工作目錄繼續，只是對話太長環境提供的 context 壓縮功能工作沒有移動，不需要可攜式檔案。
從目前對話移交給另一個 agent、同事或 repositoryhandoff下一位執行者看不到目前對話，需要一份可讀的交接文件。
目前對話繼續，另開一個支線任務給其他 agenthandoff交出與支線相關的上下文，原對話仍可繼續。

原技能會寫什麼？

官方 handoff/SKILL.md要求：在作業系統的暫存目錄寫文件；依你提供的「下一個 session 要做什麼」調整內容；列出下一位 agent 建議使用的技能；已存在的規格、ADR、issue、commit 和 diff 只引用路徑或 URL；移除金鑰、密碼和個資。它是使用者主動呼叫的技能。

實際操作：呼叫 /handoff 時，附上一句下一位要做的工作，例如「交給另一個 agent，在 prototype 目錄驗證退款狀態模型」。拿到文件後先閱讀，確認已驗證的事實、未決問題與下一步沒有混淆。官方技能寫到暫存目錄；若要跨較長時間或換環境使用，依 AI Hero 的提醒保存到可持續存取的位置。

例子：支線原型

你正在主對話討論「禮物訂單退款」，遇到一個需要跑程式才能確認的狀態模型問題。你可以讓 handoff 針對「在另一個資料夾建立原型並驗證狀態轉換」寫交接檔。第二個 agent 讀檔後做原型；主對話留在原處，稍後再吸收驗證結果。這是 AI Hero 文章特別強調的分支用法。

實戰題：何時該用 handoff？

請判斷下面兩個情境，分別選 handoff 或「同一環境的 context 壓縮功能」，並說明理由：

  1. 你與 agent 在同一個 repository 討論一小時，現在只是對話太長，下一步仍由同一個 agent 繼續實作。
  2. 你會留在目前對話設計退款流程，但要讓另一位同事在另一個 repository 驗證付款服務的 API 行為。

若第 2 題選 handoff，再寫一句你會傳給 /handoff 的任務提示。
